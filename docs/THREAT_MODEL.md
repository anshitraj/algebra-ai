# Threat Model

Scope: Project Algebra control plane (Go core), its MCP/REST surfaces, and its interfaces to merchants/payment/privacy providers. This is a living document — extend it as connectors and payment rails go from stub to real.

Methodology: enumerate the threats named explicitly in the build mandate, state the mitigation that exists **in this codebase today**, and mark anything that's a design commitment for a not-yet-built component.

## Trust boundaries

1. User ↔ Agent (authentication vs. authorization)
2. Agent ↔ Algebra (capability-scoped, revocable `AgentIdentity`)
3. Algebra ↔ Policy (server-side, deterministic, un-overridable by any LLM)
4. Algebra ↔ Privacy (alias → real value only inside `PrivacyResolver`, never to an agent)
5. Algebra ↔ Payment rails (no PAN/CVV/private-key custody, ever)
6. Tenant ↔ Algebra (capability-scoped, revocable `Tenant` bearer token — distinct from an `AgentIdentity`; a tenant administers policy/webhooks/users, it never itself spends)
7. Algebra ↔ `paymentprovider.Provider` (a scoped credential's real value crosses this boundary exactly once, wrapped in `shared.SensitiveValue`, never persisted or logged)

## Threat catalogue

| # | Threat | Mitigation today | Status |
|---|---|---|---|
| 1 | Prompt injection (merchant page/content tells the agent to exfiltrate secrets) | Merchant/browser tool results are structured data (typed Go structs), never raw page text fed back into privileged execution. MCP tool outputs cannot structurally contain PAN/CVV/OTP/key fields — those types don't exist in the MCP layer. §48 | Real (structural), full browser-content sanitization lands with the browser executor (Phase 6) |
| 2 | Malicious merchant webpage / connector response | `MerchantConnector` responses are normalized into `Product`/`CheckoutQuote` structs with bounded fields; connectors cannot inject arbitrary executable instructions into the domain layer | Real |
| 3 | Compromised agent / stolen agent token | `AgentIdentity` is scoped (`shopping.read`, `shopping.execute`, ...) and revocable (`revoked_at`); every mutating call is checked against granted permissions server-side | Real |
| 4 | Purchase replay | `Approval` binds to `(intent_id, quote_id, merchant, items_hash, amount±tolerance, currency, payment_source, expires_at)`. Executing with a consumed or expired approval is rejected | Real |
| 5 | Double payment / duplicate order | `Idempotency-Key` required on all mutation endpoints (create_intent, approve, execute, payment, place_order, cancel_order), enforced via a unique constraint + Redis fast-path, not just client discipline | Real |
| 6 | Merchant URL manipulation / SSRF | Domain allowlist + URL validation in `internal/domain/merchant` before any outbound connector call; redirect validation required before following | Real (allowlist), full SSRF egress lockdown is a deployment-layer control (Phase 6 / browser workers) |
| 7 | Browser sandbox escape | No unrestricted browser agent exists yet — `BrowserExecutor` (Phase 6) is explicitly deferred until merchant/API flows are stable, per mandate. When built: ephemeral environments, domain allowlist, navigation/timeout limits, no payment credentials in-process | Deferred by design |
| 8 | Credential / secret leakage (logs, traces, MCP results) | `internal/platform/logging` redacts authorization headers, cookies, tokens, PAN, CVV, OTP, wallet secrets by field name before any log write; redaction has unit tests asserting sensitive values never appear in log output | Real |
| 9 | Coupon manipulation | Coupon application happens inside the merchant connector / quote service against merchant-confirmed offers; the agent supplies a coupon *code* to try, never an offer *amount* — the final `CheckoutQuote.final_payable` always comes from the merchant, not client input | Real |
| 10 | Quote manipulation / stale quote execution | Quotes carry `expires_at` and `retrieved_at`. Immediately before authorization the quote is refreshed and re-checked two ways: (a) amount/items/merchant/payment-source binding via `Approval.Matches` with tolerance, and (b) a fresh `PolicyProvider.EvaluatePayment` call — a drift small enough to pass (a) can still newly cross the approval threshold and get caught by (b). Either check failing moves the intent to `REAPPROVAL_REQUIRED` instead of executing; a hard policy `DENY` at this stage is terminal (`FAILED`), not reapprovable, since re-approving unchanged terms cannot fix a cap violation | Real |
| 11 | Payment-source substitution | Approval binds to a specific `payment_source_id` (alias-resolved); execution verifies the resolved source matches what was approved before calling the vault/wallet | Real |
| 12 | Approval substitution | Approval is keyed by hash of the canonical intent representation (merchant, items, amount, currency, payment alias); a different cart/amount cannot reuse an existing approval | Real |
| 13 | Stale approval | `Approval.expires_at` enforced server-side at execution time | Real |
| 14 | Webhook spoofing | `POST /api/v1/webhooks/{provider}` (`app.WebhookService.Receive`) verifies an HMAC-SHA256 signature (constant-time compare via `hmac.Equal`) against a per-provider secret before persisting anything; a provider with no configured secret is rejected outright, not silently accepted. Deduplicated on `(provider, event_id)` (falling back to a payload fingerprint if no event ID is supplied), so a replayed delivery is a no-op, not reprocessed. Every rejection and acceptance is audited (`WebhookRejected`/`WebhookReceived`) | Real — tested (`internal/app/webhook_service_test.go`), but no real webhook-sending provider is configured (`WEBHOOK_SECRET_<PROVIDER>` unset for everything), so every inbound call is currently rejected by design until one is wired up |
| 15 | Policy override by an LLM | `PolicyProvider.Evaluate*` decisions are computed and persisted server-side from stored intent/agent/payment-source state; there is no code path where a client-supplied "decision" field is accepted or an agent can mark its own request `ALLOW`. A `DENY` is a terminal state (`POLICY_REJECTED`) with no transition out except a brand-new intent | Real |
| 16 | Agent permission escalation | Permissions are granted rows in `agent_permissions`, checked on every call; no self-service escalation endpoint exists; revocation is immediate (checked per-request, not cached past TTL) | Real |
| 17 | Sensitive data to the LLM (address, card, OTP) | `PrivacyResolver` is the only code path from alias to value; agents interact exclusively with alias strings (`shipping:home`, `payment:personal`). Card entry uses provider-hosted fields — raw PAN/CVV never transits Algebra's backend, so there is nothing to leak to an LLM in the first place | Real |
| 18 | CAPTCHA/anti-bot bypass | Explicitly out of scope by design — mandate §10/§13 prohibits it. Any connector that would need it returns `USER_INTERVENTION_REQUIRED` instead | Enforced by design |
| 19 | Fabricated integration success (fake purchase/payment/order) | Every connector/provider not backed by a real, credentialed integration returns a typed `ErrNotImplemented`/`USER_INTERVENTION_REQUIRED` rather than a synthesized success. Mock/sandbox providers set `provider_mode` explicitly and are asserted in tests to never appear as `real` | Real (structural + tested) |
| 20 | Theft of linked merchant sessions (Zepto / Swiggy OAuth tokens) | Sessions are AES-256-GCM encrypted under `ALGEBRA_MASTER_KEY` with the merchant name as AAD (a file copied to another merchant's name fails to decrypt) and bound to the endpoint they were issued for; tokens never appear in tool arguments, logs, or agent-visible output; a bearer token is never sent along a redirect | Real (tested) — file-based, one operator account per merchant; KMS-wrapped key and per-user sessions not built |
| 21 | OAuth linking attacks (code interception, CSRF, issuer mix-up, malicious metadata) | PKCE S256 required (servers without it are refused); `state` compared in constant time; RFC 9207 issuer check; RFC 8707 resource indicator, and a metadata `resource` that doesn't match the endpoint is refused; loopback-only listener with a static, single-use callback page; https-only metadata/token URLs; metadata and registration requests never follow redirects | Real (tested, `connectors/remotemcp/login_test.go`) |
| 22 | Prompt injection through merchant-supplied text (product names, tool error messages, tool names in status lines) | `connectors/sanitize` strips control, zero-width and bidi-override characters and caps length; remote tool names shown to agents must match a strict pattern. The text is still treated as untrusted data, never instructions | Real (partial by nature — sanitization can't make text trustworthy) |
| 23 | Remote MCP contract drift (a merchant changes tool shapes, so calls meant for one contract place a malformed real order) | `remotemcp.CheckTools` validates the live `tools/list` against the tools and argument names a connector uses, at startup and every minute while not ready; any mismatch disables every capability. Connectors never map tools whose schemas aren't published (Zepto) | Real (tested) |
| 24 | Duplicate real order after an ambiguous checkout (timeout or dropped stream mid-call) | MCP transport retries disabled for merchant calls; an unknown outcome, partial multi-store order, or unexpected pending-payment order returns `MERCHANT_INTERVENTION_REQUIRED`, never `FAILED` (which would invite a retry); `approvals.MarkConsumed` still prevents re-execution | Real (tested) |
| 25 | API credential leakage via redirects (Flipkart's token is a custom header net/http would forward cross-host) | Flipkart and Amazon HTTP clients never follow redirects | Real (tested) |
| 26 | Tenant-token compromise (a stolen `Tenant` bearer token used to rewrite policy, register a malicious webhook endpoint, or read another tenant's transactions) | Same scoped/revocable/hashed-at-rest bearer-token mechanism as `AgentIdentity` (`tenant.GenerateToken`/`HashToken`/`VerifyToken`, SHA-256, constant-time compare). Every `/tenants/{id}/...` route additionally checks the resolved token's own ID matches the `{id}` path segment (`requireOwnTenant`) — a valid tenant token cannot act on a *different* tenant's resources by guessing its ID. A stolen token can still set malicious policy or exfiltrate that tenant's own transaction list; there is no anomaly detection on policy changes in this build | Real (token mechanism, ownership check) — no anomaly detection |
| 27 | Scoped-credential exfiltration (a payment provider's `ScopedCredential.Value` leaking into a log, audit event, or API response) | `ScopedCredential.Value` is `shared.SensitiveValue`, whose `String()`/`MarshalJSON()` always return a redacted placeholder — `.Reveal()` is the only way to get the real value, called at exactly one site (`paymentprovider.Provider.ExecutePayment`'s caller) and nowhere else in the codebase. `audit.Event`'s forbidden-metadata-key deny-list is the belt-and-suspenders layer underneath, same as for every other secret class already in this table | Real (structural) |
| 28 | Outbound webhook forgery/tampering in transit or a malicious webhook endpoint URL used for SSRF against internal infrastructure | Every delivery is HMAC-SHA256 signed (`app.SignHMAC`, verifiable with the same construction `VerifyHMACSignature` uses) so a tenant's receiving server can reject a forged payload. A webhook URL must be a public https address (`app.ValidateWebhookURL`: no plain http, no credentials in the URL, no `localhost`/`.local`/`.internal` or bare service names, no private, loopback, link-local or otherwise reserved IP literal). Deliveries then go out through `internal/platform/safehttp`, which checks the address actually dialled, after DNS, and never follows a redirect — so a public-looking name that resolves to `169.254.169.254`, or a redirect to one, is refused, including for an endpoint registered before the URL check existed | Real (tested, `internal/app/webhook_dispatch_service_test.go`) — a network-layer egress lockdown remains a deployment control |
| 29 | Cross-user intent access (IDOR) — an agent reading, quoting, cancelling or executing another user's intent by ID | Found and fixed: intent-scoped service methods used to check only that the calling agent held a permission. `app.requireOwnedIntent` now also requires the intent's user to be the agent's user, on every intent-scoped call (discover, quotes, select, request-purchase, preview/explain, execute, order status/receipt/cancel, complete-authentication, audit trail) and the payment-intent equivalents. A foreign ID returns 404, not 403, so it doesn't confirm existence | Real (tested, `internal/app/authz_test.go`; verified over HTTP) |
| 30 | Unauthenticated agent minting — `POST /api/v1/agents` accepted any `user_id` with no credential, so anyone could mint a full-permission spending agent for any user | Found and fixed: requires a signed-in session (for yourself) or a tenant token (for the tenant's own user). `POST /api/v1/users` requires a tenant token. The old open behaviour survives only behind `ALGEBRA_DEV_AUTH=true` for local scripts | Real (verified over HTTP) |
| 31 | Human session theft / CSRF against approval endpoints | Session cookie is HttpOnly, SameSite=Lax, Secure on https, 30-day TTL, SHA-256-hashed at rest, revocable per device. Cookie-authenticated state changes with a foreign `Origin` are rejected (`csrfGuard`). Approval, payment-source, address and `/me` endpoints accept only the session — never an agent token — so neither an external MCP agent nor the app's own LLM loop can approve spend. Sign-out and password reset revoke the session's console agent too | Real (tested) — no MFA or new-device alerts yet |
| 32 | Account takeover via OAuth email linking | An OAuth identity links to an existing account by email only when the provider marks the email verified (GitHub `/user/emails` `verified`, Google `email_verified`); otherwise sign-in is refused. State + PKCE verifier live in an HMAC-signed, 10-minute, path-scoped cookie; `next` redirects are same-site paths only | Real (tested) |
| 33 | Credential stuffing / email enumeration on sign-in and reset | argon2id (m=64 MiB, t=3, p=2); unknown email and wrong password return the same error in the same time (dummy-hash verify); password reset answers identically for unknown emails; reset tokens are single-use, 30-minute, hashed at rest | Real — rate limiting is the Redis limiter above (per IP / session); no CAPTCHA or lockout |

## Rate limiting and circuit breakers (real, added post-Phase-1)

- **Rate limiting** (mandate §49): a fixed-window limiter (`internal/platform/redis.Client.Allow`) sits in front of both transports — `rateLimitMiddleware` in `internal/api/v1` (keyed by agent-token hash, falling back to source IP for unauthenticated endpoints) and in `internal/mcpserver` (keyed by the calling tool's `agent_token` argument, via `Server.AddReceivingMiddleware`). Both fail **open** on a Redis error — a cache outage must not cascade into a full API outage over a defense-in-depth control — and both are a no-op if Redis isn't configured at all (correct for local dev, not for production; see `docs/LOCAL_DEVELOPMENT.md`).
- **Circuit breakers** (mandate §38): `internal/platform/resilience.Registry` hands out one breaker per merchant-connector name; `DiscoveryService.callConnector` is the single choke point every discovery-side connector call goes through, wrapped with both the breaker and an explicit per-connector timeout (independent of whatever timeout the caller's own context carries). Proven end-to-end with a connector that always fails (`internal/app/orchestration_test.go`'s `TestOrchestration_CircuitBreaker_StopsCallingFailingConnector`) — the breaker actually stops the calls, not just exists in isolation.
- **Distributed lock** (mandate §35): `OrderService.Execute` optionally acquires a short-lived Redis lock per intent ID before doing the real work, so concurrent execution attempts on the same intent fail fast instead of all racing through the expensive path — `approvals.MarkConsumed`'s atomic compare-and-swap remains the actual correctness guarantee regardless (§32), this is purely an efficiency layer on top of it.

## Not yet mitigated (explicitly, so it isn't silently assumed)

- **No durable outbound-webhook queue** — `app.WebhookDispatchService.Dispatch` retries in-process (3 attempts, exponential backoff) on a goroutine with no persistence; an attempt that exhausts retries while the tenant's endpoint is down is lost, not queued for later.
- Full SSRF egress lockdown at the network layer (e.g., a browser worker with restrictive egress rules) — depends on the deployment platform (Phase 6 / GCE/GKE isolation, per mandate §13/§49).
- 3DS/OTP/UPI challenge UI — the `AuthorizationChallenge` domain type and `AUTHENTICATION_REQUIRED` state exist; no real PSP is wired to drive an actual challenge yet (no credentials).
- Real webhook provider integration — the endpoint, verification, and dedup are real; no provider's actual secret is configured (external prerequisite).
- Per-user merchant accounts — linked Zepto/Swiggy sessions belong to one operator account per merchant, stored in encrypted files under a static master key. Multi-user deployments need per-user sessions in Postgres and a KMS-wrapped key.
- Live verification of merchant integrations — Swiggy Instamart, Amazon, and Flipkart connectors are tested against fakes built from each merchant's published contract, not against the real services (no linked account or credentials in this environment).
